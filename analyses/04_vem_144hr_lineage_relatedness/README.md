# vem_144hr_lineage_relatedness

Same `vem_1uM_144hrsbefore` dataset as the `144hr` condition of [`vem_pretreatment`](../03_vem_pretreatment/README.md), but a different question: is a cell's morphology more similar to its **sister**'s (born from the same division) than to a random cell's? What about its **cousins**' (its parent and its parent's sister's children - sharing a grandparent, not a parent)?

Frame 7 is day 0 (drug addition). Frames 1-`config.BEFORE_DRUG_END_FRAME` (5, for now) are **before-drug** - effectively naive growth. Frames `config.AFTER_DRUG_START_FRAME` (7, fixed by the data) through `config.AFTER_DRUG_END_FRAME` (11, for now) are **after-drug**. Frame 6 (day -1, the frame immediately before day 0) is currently missing from the raw data entirely, and falls outside both named ranges above - `select_cells.py` and the lineage-tree build both skip any empty frame gracefully, same as they would any other. A third, wholly separate **naive** condition (`config.CONDITIONS['naive']`) is included as a sanity-check control, sampled and CAJAL'd entirely on its own over the same number of frames as the before-drug window (1-`config.BEFORE_DRUG_END_FRAME`) - it should look like before-drug, since neither has seen a drug yet. All three questions (sisters vs. random, cousins vs. random) are asked separately for each of the three groups, so a change after-drug can be compared against both before-drug and a cell line that was never treated at all.

**Before-drug, after-drug, and naive are each their own separate CAJAL run** (`output/before-drug/`, `output/after-drug/`, `output/naive/` - three subtrees, not two). Before-drug and after-drug used to be pooled into one combined `vem` run spanning frames 1-`AFTER_DRUG_END_FRAME`, split into before/after only when building sister/cousin pairs in the notebook. Since each group's test is self-contained (its real pairs are only ever compared against that SAME group's own null - see `01_relatedness.ipynb`'s Method below), neither group ever needed the other's distances, so splitting the combined run loses nothing. CAJAL's GW distance computation is quadratic in cell count, so two half-sized runs cost roughly **half** what one combined run of the same per-frame sample size did - that saved compute is spent as a deeper per-frame sample (`SAMPLE_SIZE_PER_FRAME = 1500`, up from the old combined run's 1000) rather than banked, at roughly the same total wall-clock. Before-drug and after-drug still share **one lineage tree** (`config.TREE_DATASETS['vem']`, built once from `vem`'s FULL metadata across its whole span) even though they're two separate CAJAL runs, since they're two frame-windows of the exact same tracked lineages; naive has its own, wholly separate tree.

1. **Selects cells** with a flat per-frame subsample, one CAJAL run per condition now (before-drug: frames 1-`config.BEFORE_DRUG_END_FRAME`; after-drug: frames `config.AFTER_DRUG_START_FRAME`-`config.AFTER_DRUG_END_FRAME`; naive: frames 1-`config.BEFORE_DRUG_END_FRAME`, its own separate run) - no subclass stratification (this analysis never classifies cells), and deliberately lineage-unaware: which true sister/cousin pairs end up with both members sampled is left to chance, not biased towards keeping more of them (`select_cells.py`).
2. **Runs CAJAL** once per modality (cell, nucleus) per condition. No UMAP/PHATE embedding, same as the `_pretreatment` analyses: the question needs the real distances, not a 2D projection that distorts them.
3. **Reconstructs each lineage tree** directly from its FULL `{drug}_metadata.csv` (not just the CAJAL-sampled cells - see below) using its `node_id`/`pred_node_id`/`lin_id` columns, and finds every sister pair and cousin pair in it (`shared/lineage_tree.py`). This is intentionally **not** based on `lineage_frame7_to_frame1.mat` (that file only resolves each day-0 lineage's single frame-1 ancestor, collapsing every division in between - the generation-by-generation structure this analysis needs isn't in it; `naive` doesn't even have such a file, having no day-0 drug-addition event to anchor one).
4. **`01_relatedness.ipynb`**: for each modality and each group (before-drug, after-drug, naive), restricts each sister/cousin pair to whichever of their own cells actually survived CAJAL subsampling (every surviving frame combination on each side counts as its own pair - sisters and cousins alike are not required to share a frame, since a cousin pair's two parents can divide at different times), builds ONE shared null distribution of *individual* random-pair distances drawn from every CAJAL-embedded cell in that group (any frame), and compares the real sister-pair and real cousin-pair distance *distributions* against it via a one-sided Mann-Whitney U test - not a single collapsed mean against a null of means, which would hide whether the effect holds for most real pairs or is driven by just a few (`shared/pair_similarity.py`'s `pair_distance_permutation_test` + `plot_pair_similarity_test`). One figure per (modality, group) - up to 6 total. Alongside each p-value, `pair_distance_permutation_test` also returns a rank-biserial correlation effect size (`r = 1 - 2U/(n1*n2)`, bounded `[-1, 1]`) - a p-value alone conflates effect size with sample size (with enough pairs, even a tiny real shift becomes extremely significant), so the effect size is what actually says how big the difference is, not just how sure we are it's nonzero.

---

## Why the full metadata, not just the sampled cells

`main.py` only sends a subsample of cells through CAJAL (mask extraction and the GW distance computation don't scale to every cell). But a sister/cousin *relationship* is a fact about the real lineage tree, independent of which cells happened to get sampled - resolving it from the subsample alone would silently miss (or misidentify) relationships that pass through unsampled intermediate rows. Each notebook therefore reads the relevant tree's full, unsampled metadata (`config.TREE_DATASETS[tree]`, via `config.metadata_csv_path()`) to build it, and only afterwards checks which of each relationship's own cells are also in a given group's own `selected_metadata.csv`/CAJAL output.

## Configuration

`config.py`'s `CONDITIONS` dict holds each of the three CAJAL runs' (before-drug, after-drug, naive) own drug name, `(min_frame, max_frame)` sampling window, and which lineage tree its sister/cousin pairs come from (`'tree'`: `'vem'` for before-drug and after-drug, `'naive'` for naive). `TREE_DATASETS` holds each of the two underlying lineage trees' (`vem`, `naive`) own drug name and full span - read once and shared by every `CONDITIONS` entry with a matching `'tree'`. `AFTER_DRUG_START_FRAME` (fixed - frame 7, when the drug was actually added), `BEFORE_DRUG_END_FRAME`/`AFTER_DRUG_END_FRAME` (this analysis's own tunable range limits - `BEFORE_DRUG_END_FRAME` also sets naive's comparison window length), `SAMPLE_SIZE_PER_FRAME`, and the pair-similarity test's `N_NULL_SAMPLES`/`TEST_SEED`. `output_dir()`/`masks_dir()`/`cajal_output_dir()` take a `condition` argument (`before-drug`, `after-drug`, or `naive` - each processed and stored entirely separately); `metadata_csv_path()` takes a `drug` name directly, since `TREE_DATASETS` and `CONDITIONS` are keyed differently but can share a metadata file.

**Note**: splitting before-drug/after-drug into separate CAJAL runs means any CAJAL output cached from before this change (a single combined `output/vem/` subtree) is no longer valid for this analysis and needs to be recomputed on Quest.
